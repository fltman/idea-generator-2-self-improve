# Idégeneratorn, self-improving

[![Support me on Patreon](https://img.shields.io/badge/Patreon-Support%20my%20work-FF424D?style=flat&logo=patreon&logoColor=white)](https://www.patreon.com/AndersBjarby)

An experiment: an idea generator that thinks about how to improve **itself**, and a Claude Code agent that builds the best of those ideas into its code while it runs.

It is a fork of [Idea Generator 2](https://github.com/fltman/idea-generator-2), an idea board where language models branch, cross and judge ideas and an evolution autopilot breeds the best ones. This fork adds three things:

1. **Claude Code is the model.** Every role (branch, cross, judge, summary, brief…) runs on the local `claude` CLI headless, using your own Claude login. No API key is needed in the app. Only the X scout stays on OpenRouter, since Grok is the only route that can search X.
2. **A self-improvement board.** Its goal is to make this app a better idea generator. Every prompt on it gets the app's current README feature list and the list of features the loop has already built, so the ideas are concrete changes to this codebase. The jury is told what "buildable in one session" means here.
3. **A builder.** When an idea on that board gets gold (from the jury, or from you), the server hands it to a headless Claude Code agent in its own git worktree. The agent implements it, adds tests, takes before/after screenshots and writes a journal entry. The server then checks the work itself (`npm test` plus booting the new server) and merges it into `main`. The running app restarts and the page reloads with the new feature. Every build, including the failures, leaves a write-up in [`journal/`](journal/INDEX.md), so the whole history can later be cut into a film.

## The loop

```
seed → branch / cross (claudecode:sonnet) → jury (calibrated, claudecode:sonnet)
     → 🥇 gold → builder: git worktree → claude -p (opus) builds, tests, screenshots, journal, commit
     → server re-runs npm test + boot check → merge --no-ff into main → app restarts, browser reloads
     → README grows → next generation of ideas knows the new feature
```

- **One build at a time.** The jury may start `buildsPerDay` builds per board per day (default 4). Builds you start by hand are not capped. Each build's agent has a budget (`BUILD_MAX_USD`, default 15) and a one-hour timeout.
- **Verified by the server, not the agent.** The builder re-runs the tests and boots the server from the worktree before it merges. A failing build keeps its branch (`build/NNNN-slug`) and still gets its journal entry in `main`.
- **Scoped agent.** The agent runs with `--permission-mode acceptEdits` and an explicit tool allowlist: file edits in its worktree, `npm test`, `node tools/shoot.ts`, and local git (add, commit, diff, log). Everything else is denied automatically, including push, checkout, reset, merge, rm, curl, npm install and web access. Running the tests does run code the agent wrote, so the worktree and the jury gate are the boundary, as in any CI.
- **Not pushed by default.** Merges stay local until you push. Set `BUILD_PUSH=1` to push `main` after each merge.
- **Progress camera.** The server screenshots the live board into `progress/` (gitignored): every 10 minutes (`CAMERA_MINUTES`, `CAMERA=0` turns it off), at every gold idea, when a build starts or ends, and after every restart, which includes right after a merge. `progress/latest.png` is always the newest picture, and `progress/README.md` logs every one inline, so you can follow along in any Markdown viewer and later cut it into a timelapse.
- **Live.** A ticker in the corner streams what the agent is doing (reads, edits, commands, its own remarks). 🔨 **Builds** in the top bar shows every build with its summary, cost, screenshots, journal and full log.

## What it does

- **Boards with their own goal and setup.** Each board has its own creation flow (prompts), jury guidance, scouts, models, autopilot and limits. Templates only seed a new board.
- **Canvas.** Infinite pan and zoom with a force layout, so families cluster. Drag an idea onto another to cross them. Hovering lights up an idea's whole lineage, and a ball grows with its score.
- **Explainable jury.** Originality, feasibility and impact are scored 1–5 each, with a one-sentence reason and 2–4 keywords. The medal is computed in code: bronze from 9/15, silver from 11, gold from 13. It is calibrated against reference ideas (`npm run calibrate`), and gold is rare on purpose.
- **Evolution autopilot (server-side).** Boards set to *automatic* breed parents by tournament selection on the jury score, and now and then expand a strong idea instead. The autopilot keeps running with no browser open, within its limits:
  - steps per hour
  - USD per day per board
  - a global USD per day
  - error backoff
- **Lift recipes with a measured hit rate.** For every idea the jury also writes a *lift recipe*: the one change that would earn it the next medal, typed by the criterion it raises (originality, feasibility or impact). Every child bred from that idea, by hand or by the autopilot, gets the recipe as its task and remembers its parent's medal; once the child is judged, the recipe either lifted the medal or it did not. The idea panel shows the recipe, how often recipes of that type have worked on the board, and for a child its task and ✓/✗. The overview shows the hits per type. Breeding uses the numbers: a cross hands on whichever parent's recipe type has the better record, and in tournament selection the hit rate nudges the score by at most ±0.5, so it breaks ties between ideas the jury scored the same but never outweighs a point of score.
- **Placebo trials for recipes.** Do recipes beat chance? One breed in five that would have been handed a recipe is handed a placebo instead, by lot: the vague task "improve it", with no criterion and no recipe. The child remembers which recipe type was withheld. A breed from a parent below gold that has no recipe is a third, no-task arm. Every arm counts a hit the same way (the child's medal above its parent's). The overview's *Lift recipes vs. placebo* table shows hits per type for the recipe and placebo arms side by side, the no-task arm in total, and a plain reading: *too early to tell* until both arms have 10 judged children, then whether recipes beat placebo, make no clear difference (within 10 points) or lose to it. A child's panel says *Placebo from …* or *Control from …*. Only the recipe arm feeds the hit rate that steers breeding, so a placebo's luck never steers selection.
- **Control siblings and net lift.** A raw hit rate cannot tell a recipe's effect from luck or from regression to the mean. So every fourth recipe cross the autopilot makes gets a *control sibling*: the same two parents crossed again in the same step with no task at all, remembering the withheld recipe type and the same parent medal. The net lift of a recipe type is the mean medal gain (in medal steps, falls count too) of its recipe children minus that of its control siblings. Under the placebo table the overview shows one chip per type, e.g. *Feasibility +0.40 · n 50/1* (recipe children / control siblings), green above zero, red below, *–* until both arms have data. A recipe's panel shows the same line for its type, and a control sibling's panel says *Control sibling from …*. Once a type has a net lift, it replaces the hit rate as the tie-breaking nudge in tournament selection, still strictly within ±0.5 and shrunk while there are few controls. It costs about one extra cross and judgement per four recipe crosses. Hand crosses and expands get no control.
- **Recipe check: applied or ignored.** A child handed a recipe may simply not carry it out, and then its medal says nothing about the recipe. So after the jury's verdict on a recipe child, the judge model is shown the parent, the recipe and the child (no scores, no medals) and rules whether the child really applied the recipe, with a one-sentence reason. The child's panel says *✓ recipe applied* or *✗ recipe ignored*. An ignored recipe counts as neither hit nor miss in the hit rate that steers breeding. Under the net-lift chips the overview splits the recipe arm's hit rate into *Applied*, *Ignored* and *Unchecked* (older children, or a check that failed; they still count as before). One extra call per recipe child, once: re-judging does not re-check. The placebo table and net lift keep every recipe child (intention to treat).
- **Blind duel decides recipe hits.** A medal is a coarse ruler: a recipe can sharpen a child without crossing a threshold, and noise can push one across. So after the verdict on a recipe child, the judge model also reads child and parent side by side as "A" and "B", in an order decided by a coin, with no recipe, scores, medals or lineage, and names a winner per criterion (or a tie). The recipe hit is now the child winning the recipe's own criterion; a tie or a parent win is a miss. The medal and scores stay exactly what the jury gave. The child's panel shows three badges (▲ child won, ▼ parent won, = tie; the recipe's criterion ringed) and *✓ recipe hit* or *✗ recipe miss*. The overview shows, for the same children, how many won their criterion in the duel against how many rose a medal, and the per-criterion tally. One more call per recipe child, once. Children without a duel (older ones, or a failed duel) keep the medal rule. The placebo table and net lift still use the medal, because placebo and control children are not duelled.
- **Idea styles drawn by lot.** Which framing earns medals? Every breed (expand or cross, by hand or by the autopilot) draws one of four styles by lot: *scenario* (one concrete moment where someone uses it), *mechanism* (how it works and the step that drives it), *analogy* (something that works elsewhere, mapped here) or *metric* (the number it moves, how it is measured, a target). The breeding prompt demands that style, and the child remembers it. The jury never sees it. The idea panel shows a small ✎ tag with the style; the overview's *Style by lot, medal rate* table shows per style the judged children (n), how many earned a medal (bronze or better) with the rate, and how many gold, with *too early* beside every style under 10 judged children. Styles are only measured; they never steer selection.
- **Wording gap: a blinded-review test for the jury.** Does an idea score well for what it says, or for how it says it? With *Wording gap* ticked in a board's jury settings (on by default for boards made by `self:setup` with its default focus), every verdict is followed by two more calls on the judge model: it rewrites the idea in plain, neutral wording (same claims, mechanism and numbers; no catchy name, metaphor, scene or hype), and the ordinary jury prompt scores that rewrite without seeing the first verdict. The gap is the jury's sum minus the plain sum; above one point (the judge's own run-to-run spread) the idea is *style-carried*. The idea panel shows *Jury 10 → plain rewrite 8 · gap +2*, the verdict, the rewrite and its reason, and a *Rescore a plain rewrite* button that does it by hand on any board. The overview's *Wording gap per keyword* table shows, per first keyword, how many rescored ideas were style-carried and the mean gap. Measured only: the medal, selection and the builder never read it.
- **The scrap heap: wilted ideas get one more try.** An idea has *wilted* when it has bred five or more judged children and none rose above its own medal: selection keeps picking it, and it keeps passing nothing on. With *Scrap heap* ticked in a board's autopilot settings (on by default for boards made by `self:setup` with its default focus), every 8 bred ideas, or whenever the autopilot has nothing else to do, it draws one wilted idea by lot, weighted by how unlike the living pool its keywords are, and crosses it with the fittest living idea through the ordinary cross prompt. The task is the jury's own reason for the wilted idea's score: *the new idea must overcome what this verdict says held it back*. Each wilted idea is drawn once. The child is judged at once and breeds like any other idea; it stays out of the recipe, placebo and control trials. The overview's *Scrap heap* card shows how many wilted ideas wait and how many were drawn, the medal rate (bronze or better) of scrap children against normal breeds, the gap in points against a target of +10 (*too early* under 10 judged scrap children), the mean keyword distance of the draws, and the survivors (scrap children with a medal) as links. A scrap child's panel says *Scrap child of "…"* with a link to the wilted idea.
- **The flight recorder: every model call on the record, and crashes survived.** Each model call is written to a `calls` table before it starts (role, idea, model) and closed when it ends with its dollars and seconds, or marked failed. A row still open when the server starts again was cut off by a crash or restart: the boot marks it *lost*, and once the browser hands over its settings, a cut-off judgement (or second opinion on a medal edge) is queued again for its idea, if that idea is still unjudged. Breeds, summaries and scouts are not redone, so a restart never adds ideas. The overview's *Flight recorder* card shows calls, dollars and seconds in total, and per role (judge, combine, expand, duel, liftcheck, plain, retrial, …) the calls with their failures and cut-offs, and dollars and seconds per medal (the role's total over all the board's bronze-or-better ideas). A chip counts the server restarts since the board was made and the calls they cut off on it. A test kills a real server process with `SIGKILL` in the middle of a judgement, starts it again on the same database and checks there is one idea row, one lost judge call and exactly one finished one.
- **Diversity pressure against monocultures.** Tournament selection keeps crossing the strongest ideas, and those tend to share one theme. The autopilot measures how concentrated the board is: the share of the last 24 bred ideas that carry the jury's most common keyword. From 60% on (with at least 12 tagged ideas) the board is a *monoculture*, and every autopilot step takes at least one parent from outside that theme, or expands the best idea outside it. Within that smaller pool the tournament still ranks by jury score. The child remembers the theme it was bred to escape. The overview's *Diversity* gauge draws the top theme's share after every bred idea, with the monoculture line, names the theme, says since which idea the current monoculture has run, and counts the breeds made outside it and how many of them the jury really tagged with something else. Such a child's panel says *Diversity pressure: bred outside the "…" monoculture*.
- **A second opinion on borderline verdicts.** A jury sum exactly on a medal threshold (9, 11 or 13) is one point from a different medal. On a self-improvement board such a verdict is re-scored in the background by a second judge on another model (the *Second judge* role, default `claudecode:opus`), which runs the same judge prompt and never sees the first verdict. The idea panel shows a confidence band on the 3–15 scale with the medal lines, both sums, the second judge's reason and whether the medals agree. The medal stays the jury's, but in tournament selection a disagreement costs the idea half the gap (a 13 that the second judge puts at 11 breeds like a 12). On any board, *Ask a second judge* in the panel does the same by hand. Re-judging clears the old second opinion.
- **Gold on the line waits for the second judge.** On a self-improvement board a jury 13 no longer starts a build at once. The panel says *the build waits for the blind second judge*; the build is queued only if the second judge also gives gold. If it gives less, the idea is *contested*: the panel says so with both sums, a toast tells the board, and the Builds view lists it under *Contested gold – waiting for a human* with a *Build anyway* button. A clear gold (14–15) and gold set by hand still build at once.
- **Scouts.**
  - *X trends*: Grok with live X search via OpenRouter. A lead is kept only if its post is among the search engine's own citations.
  - *AI research*: Hugging Face daily and semantic paper search, aimed at the goal.
  - Drag a lead onto the board to seed it.
- **Across boards.**
  - *Announce* an idea to other boards. It arrives as a guest, is judged against the new board's goal, and cross-breeds there.
  - Spin an idea off into a *new board* where it is the goal.
  - *Spores* 🍄: tick *Spores* in a board's autopilot settings and the board both sends and takes in ideas on its own. Every 10 bred ideas the autopilot sends the board's strongest idea (silver or better, never sent before, never one that is already built) to the other spore board whose own top keywords it shares most (a random draw breaks ties, so with no overlap a spore drifts blind). It lands as a guest, is judged against that board's goal and cross-breeds with the locals; with a medal there it has *taken root* 🌱. The overview's *Spores* card shows how many left and rooted, where they landed, and how many arrived, rooted and bred children; a spore's panel says *Spore from …* and whether it took root. Off by default.
- **Boards for your own codebase.** *New board → 📁 From codebase*: give a local folder, press *Analyse*, and the app reads the file tree, the README, CLAUDE.md and package manifests (with little documentation, the start of the likeliest entry files). It runs none of the project's code, skips `node_modules`, `.git`, dotfiles and symlinks, and caps what it reads. The model describes the code and proposes 4–6 directions, each with a reason drawn from the files and a starter idea; you tick the ones you want (features, UX, performance, tests, …) or write your own. The board is created with those directions as its goal, a jury that judges feasibility and originality against that code, the scan in every prompt, one seed per direction, and the autopilot running. Gold ideas are appended to a Markdown file (`data/gold/board-N-name.md`, shown in the board settings), from the jury or by hand. Building them into the codebase with Claude Code is the next step.
- **Self-improvement.** A board marked *self-improvement* proposes changes to this app, and its gold ideas are built in by Claude Code (see [The loop](#the-loop)). An idea's panel there has 🔨 *Build it into the app* instead of the project button, and setting its medal to 🥇 by hand starts a build too.
- **Claude Code projects.** One click, or the jury on gold, writes a folder containing `CLAUDE.md` (brief, MVP, first steps, open questions, lineage, verdict), `README.md`, `idea.json`, a gitignored `vault/`, and runs `git init`.
- **Board summary, keyword trend dashboard, report.**
  - *Summary*: themes, strongest ideas, gaps and next steps for one board.
  - *Dashboard*: keyword trends across boards, with sparklines and drill-down.
  - *Report*: totals, cross-board conclusions, every project with its start command, and one card per board. Exports to Markdown.
- **Exhibition mode.** Fullscreen, the camera follows new ideas, and visitors type seeds. It runs together with automatic mode.
- **Providers per role.** Every role has its own model, written `provider:model`. The roles are distill, branch, cross, judge, summary, research scout, X scout, project brief and second judge.
  - **Claude Code:** `claudecode:sonnet`, `claudecode:opus`, `claudecode:haiku` or a full model ID. Runs the local `claude` CLI headless with no tools and no settings, one process per call (2–5 s).
  - **Hosted:** OpenRouter, Anthropic (official SDK) and OpenAI.
  - **Copilot models:** neither GitHub Copilot nor Microsoft Copilot has a completion API for apps, and GitHub Models was retired on 30 July 2026. GitHub points to Microsoft Foundry, so the models behind both Copilots are reached through the Azure OpenAI / Microsoft Foundry provider.
  - **Local:** Ollama, MLX (`mlx_lm.server`), LM Studio, or any OpenAI-compatible URL.
- **Swedish and English** interface. Generated text follows the language of its seed.

## Run

Needs Node 25 or newer, which runs TypeScript directly (there is no build step), Claude Code installed and logged in (`claude`), git, and Google Chrome for the journal screenshots.

```bash
npm install             # one dependency: @anthropic-ai/sdk
npm run dev             # http://localhost:8301 — restarts itself when a build is merged
npm run self:setup      # once, in another terminal: creates the self-improvement board (autopilot on)
npm test                # 129 tests, fake LLM, fake claude CLI, fake agent; no network
npm run calibrate       # real judge vs. reference ideas (claudecode:sonnet ≈ $0.13)
npm run shoot -- --help # the screenshot tool the builder's agent uses
```

Use `npm run dev`, not `npm start`, for the loop: a merge changes `server/`, and only the watcher restarts the server so the new code runs. The default port is 8301 rather than the original app's 8300, so both can run at once and each keeps its own browser settings.

All app settings live in the browser (localStorage), including API keys, models per role, provider addresses, the projects folder and the global budget. The browser pushes them to the local server, which keeps them in memory only and never writes keys to disk. Environment variables (`OPENROUTER_API_KEY`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `AZURE_OPENAI_API_KEY`) work as a fallback. The self-improvement board sets its own models, so it runs on Claude Code even with no browser open.

| Variable | Default | |
|---|---|---|
| `PORT`, `HOST`, `DB_FILE` | 8301, 127.0.0.1, `data/ideas.db` | |
| `BUILD_PUSH` | off | `1` pushes `main` after each merged build |
| `BUILD_MAX_USD` | 15 | budget per build (`claude --max-budget-usd`) |
| `CLAUDE_BIN` | `claude` | the CLI the builder runs |
| `CAMERA_MINUTES`, `CAMERA` | 10, on | timelapse interval for `progress/`; `CAMERA=0` turns the camera off |
| `IDEAGEN_NO_BUILDER`, `IDEAGEN_NO_AUTOPILOT` | off | `1` turns them off (screenshots and boot checks do this) |

The server listens on 127.0.0.1 only. There is no login, and keys pass through it, so **do not expose it** as is.
